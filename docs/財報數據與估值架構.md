# 財報數據與估值架構

- 日期：2026-11-18（澳門時間）
- 目的：回答三個問題，作為 alpha.3（財報數據）與 beta.1（估值方法）的設計依據：
  1. 財報數據由申報層到標準層、檢查層，以及調整與估值，怎樣專業化、系統化處理？
  2. 會計準則改變時能否正確應對？系統有沒有適應變化的彈性？
  3. 會否抽離成獨立程式庫，方便維護？
- 承接：`docs/決策紀錄與路線圖-v2.1.md` §3（四層架構與檢查規則）、`docs/引擎審查-2026-11.md`。

---

## 1. 現況（如實說明）

| 環節 | 現在怎樣做 | 差距 |
| --- | --- | --- |
| 申報層 | **未有**。只用 Yahoo 已整理過的科目，看不到公司原始申報科目 | 無法追溯到申報文件、科目與期間 |
| 標準層 | **未有獨立一層**。`generic_spec.py` 以「科目名稱清單」直接取 Yahoo 數字（例如 `EBIT_ROWS`） | 對照規則寫在程式碼內；沒有版本、沒有生效日期 |
| 檢查層 | **未有**。只有估值結果的算術驗證（`verify_fcff`），沒有對財報本身做勾稽 | 錯誤數據可直接進入估值 |
| 數據調整 | 已有：用戶逐項修改財報數字，必須寫理由，原值保留，調整紀錄寫入 Excel（R04–R07） | 只有人手調整；沒有規則化的正常化（一次性項目等） |
| 估值計算 | FCFF DCF 引擎＋獨立驗證；2026-11 審查後，數據取用和假設已按業界標準修正 | 只有一種方法；方法沒有統一的介面 |
| 市場數據 | 已有：每日累積、未調整價格、公司行動、總回報與來源核對、修訂紀錄 | — |

結論：**數據層的專業化正是 alpha.3 要做的事**。下文是目標設計。

## 2. 目標：四層數據管線

```
來源（SEC XBRL、Yahoo、年報 PDF、日後的付費數據商）
   │  數據來源介面：fetch() → 原始文件
   ▼
① 原始層   原樣保存＋SHA-256＋來源網址＋抓取時間；永不修改
   ▼
② 申報層   每個數字一筆「申報事實」：公司、原始科目（us-gaap:Revenues、ifrs-full:Revenue…）、
           分類法版本、數值、單位、倍數、貨幣、期間、時點／期間、申報類型、文件編號、申報日、分部維度
   ▼  對照規則（版本化資料，不是程式碼）
③ 標準層   SV 標準科目（按行業模板：一般企業、銀行、保險）；每個值記錄：用了哪些申報事實、哪一版規則
   ▼  檢查規則（版本化資料）
④ 檢查層   勾稽、報表互連、每股、單位、期間連續、跨來源、重編、異常變動 → 每期數據品質等級
   ▼
調整層     ①人手調整（現有，留痕）②規則化正常化（一次性項目、租賃、金融子公司…）③ AI 建議（T1，需用戶採用）
   ▼
估值層     方法登記表：FCFF、DDM、剩餘收益、P/B–ROE、反向 DCF、相對估值…；同一套輸入介面
```

### 2.1 標準化：對照規則是「資料」，不是程式碼

對照規則以版本化的設定檔維護（YAML），每條規則包含：

```yaml
- standard_item: operating_income          # SV 標準科目
  template: [general]                      # 適用行業模板
  taxonomies: [us-gaap, ifrs-full]
  effective_from: 2000-01-01               # 適用的會計期間（期初日）
  effective_to: 2026-12-31
  sources:                                 # 依優先次序
    - concept: us-gaap:OperatingIncomeLoss
    - concept: ifrs-full:ProfitLossFromOperatingActivities
    - formula: revenue - cost_of_revenue - operating_expenses
  sign: credit
  notes: IFRS 18 之前 IFRS 沒有強制的「營業利潤」小計
- standard_item: operating_income
  template: [general]
  taxonomies: [ifrs-full]
  effective_from: 2027-01-01               # IFRS 18 起
  sources:
    - concept: ifrs-full:OperatingProfitLoss   # IFRS 18 定義的 operating profit 小計
  notes: IFRS 18 第 69 段；分類方式與舊口徑不同，見重編處理
```

- 每個標準值保存「規則版本＋生效區間＋使用的申報事實」，任何數字都能追溯「為甚麼是這個數」。
- 規則改動經測試（見 §5）才能合併；舊版本保留，回看舊估值時用當時的版本。

### 2.2 會計準則改變：怎樣應對

| 機制 | 作用 |
| --- | --- |
| **按會計期間生效的規則** | 同一個標準科目可以有多條規則，按報告期間自動選用。2026 年報用舊規則，2027 年報用新規則 |
| **分類法版本** | 申報層保存每個數字的分類法版本（us-gaap 2026、ifrs-full 2027…），新增或棄用的科目由對照規則處理 |
| **口徑變化標記** | 準則改變導致前後期不可比時，標準值加「口徑變更」標記，財報頁並排顯示，增長率與比率不跨口徑計算 |
| **重編與過渡期** | 公司按新準則重編比較期數字時，申報層保存兩個版本；標準層以「最新可比口徑」為主，保留原始公布值 |
| **重新標準化** | 規則更新後，對已保存的申報事實重新執行標準層（不需重新下載）；新舊結果都保留，差異列入報告 |
| **估值時點正確** | 每次估值記錄所用的數據批次與規則版本，回看舊估值完全可重現 |

**已知會到來的準則變化（須預先處理）：**

| 準則 | 生效 | 影響 | 系統處理 |
| --- | --- | --- | --- |
| **IFRS 18《財務報表的列報與披露》**（香港：HKFRS 18） | 2027-01-01 起的年度 | 損益表分為經營、投資、融資類別，強制「經營利潤」與「融資及所得稅前利潤」小計；管理層業績指標須披露 | 新增 IFRS 18 的對照規則（2027 起生效）；聯營收益改列投資類別，EBIT 口徑因此改變，須標記口徑變更 |
| **ASU 2024-03**（費用細分披露，美國） | 2026-12-15 後開始的年度 | 損益表費用按性質細分（存貨、員工薪酬、折舊、攤銷等） | 新科目進入申報層；D&A、員工成本更精確 |
| **ASU 2023-07**（分部報告，美國） | 已生效 | 分部重大費用披露 | 供分部拆解（T8）與金融子公司分拆（審查 S12）使用 |
| **ASU 2023-09**（所得稅披露，美國） | 已生效 | 有效稅率對賬細分 | 稅率過渡（E6）可改用公司披露的對賬項 |
| **IFRS 16／ASC 842**（租賃） | 已生效 | 國際準則把租賃列作債務；美國經營租賃費用仍在營業利潤內 | 按準則分別處理租賃負債是否入債務（審查 S2） |
| **IFRS 17**（保險合約） | 已生效 | 保險業損益結構完全不同 | 保險模板的對照規則 |

### 2.3 檢查層與數據品質

- 檢查規則同樣是版本化資料（規則、容許誤差、嚴重程度、適用模板），詳見路線圖 §3.6。
- 每家公司每期得出品質等級；「錯誤」級別未處理的期間不會自動進入估值。
- 跨來源核對（SEC 與 Yahoo、日後的付費數據商）差異超過門檻即標示；數據商接入前用同一套檢查評估（路線圖 §3.8）。

### 2.4 調整的三種來源，同一條留痕

| 來源 | 例子 | 生效方式 |
| --- | --- | --- |
| 人手調整（已有） | 用戶修正單位錯誤、剔除一次性收益 | 必須寫理由，原值保留 |
| 規則化正常化（新增） | 減值、重組、出售收益、訴訟和解自動列為一次性項目；租賃與金融子公司按準則處理 | 規則版本化，結果可關閉 |
| AI 建議（T1） | 從附註找出未在報表標示的一次性項目 | 只是建議，用戶按「採用」才生效 |

三者寫入同一個調整紀錄（誰、何時、原值、新值、理由、依據），估值與 Excel 都列出採用了哪些調整。

### 2.5 估值方法：統一介面

```python
class ValuationMethod(Protocol):
    key: str                                   # "fcff" | "ddm" | "ri" | "pb_roe" | "reverse_dcf" | "relative"
    applies_to: set[str]                       # 行業模板
    def inputs_needed(self) -> list[str]: ...  # 需要的標準科目
    def value(self, data: StandardisedData, market: MarketInputs, assumptions: Assumptions) -> MethodResult: ...
    def verify(self, result: MethodResult) -> list[str]: ...   # 獨立重算，與現有 verify_fcff 同一原則
```

- 新方法只要實作這個介面並登記，就能加入綜合理論價和足球場圖；引擎與數據層互不依賴。
- 每個方法都有獨立驗證，以及一份「已知答案」的測試數據（例如以教科書案例核對）。

## 3. 抽離成獨立程式庫

**會抽離。** 估值與數據處理是本系統的核心資產，應獨立於網頁、API 和任何前端。

```
libs/
├── sv_data/          財報數據：來源介面、原始層、申報層、標準層、檢查層、調整層
│   ├── rules/        對照規則與檢查規則（YAML，版本化）
│   └── tests/
├── sv_valuation/     估值：方法介面、FCFF（現有引擎遷入）、DDM、RI、反向 DCF、相對估值、獨立驗證
│   └── tests/
└── sv_market/        市場數據：價格、公司行動、總回報、匯率（現時在 backend/app/services/market.py）
backend/              API、用戶、排程：只呼叫上面三個程式庫
src/                  v1 命令列與網頁：過渡期保留，逐步改為呼叫程式庫，之後移除
```

| 原則 | 做法 |
| --- | --- |
| 單向依賴 | `sv_valuation` 只讀標準化數據，不知道數據從哪裡來；`sv_data` 不知道有估值 |
| 純函數優先 | 計算不連網、不寫檔；輸入相同結果必定相同，方便測試與重現 |
| 各自版本 | 每個程式庫有自己的版本號與 CHANGELOG；每次估值記錄所用的程式庫與規則版本 |
| 可獨立發佈 | 有自己的 `pyproject.toml`，日後可供其他系統或研究筆記本使用 |

**遷移步驟：**

1. alpha.3：新建 `libs/sv_data`，四層數據管線直接在程式庫內開發；`generic_spec` 改為讀標準層。
2. alpha.3：`backend/app/services/market.py` 移入 `libs/sv_market`（只搬位置，行為不變）。
3. beta.1：`src/engine` 移入 `libs/sv_valuation` 並套上方法介面；DDM、RI、反向 DCF 在程式庫內開發。
4. beta.1 之後：v1 網頁停用；命令列改為呼叫程式庫。

## 4. 適應變化的彈性

| 變化 | 系統怎樣應對 |
| --- | --- |
| 會計準則改變 | 新增按期間生效的對照規則與檢查規則（§2.2），重新標準化已保存的數據 |
| 數據來源失效或更換 | 數據來源介面；多來源互相核對；任何來源失效都在資料缺口標明 |
| 付費數據商接入 | 實作同一個來源介面，經檢查層評估後才採用 |
| 新的估值方法 | 實作方法介面並登記（§2.5） |
| 新市場、新貨幣 | 無風險利率、稅率、國家風險按模型貨幣與業務所在地取值（引擎審查 E1、E6、E8），新增市場只需補數據來源與參數表 |
| 參數過期（ERP、CRP、β 表、稅率） | 參數按日期保存歷史並自動更新；過期即在資料缺口標明（ERP 已完成，其餘見審查 S5） |
| AI 模型更換 | AI 只做提案與解釋，結果經 Schema 與引用驗證；更換模型不影響計算 |

## 5. 品質保證

- **黃金數據集**：每個行業模板挑選 10–20 家公司，標準化數字與年報原文逐項核對後凍結，作為回歸測試；規則改動必須通過全部黃金數據。
- **規則測試**：每條對照規則與檢查規則都有正反例測試。
- **獨立驗證**：每個估值方法都有不依賴引擎的重算（沿用 `verify_fcff` 的做法）。
- **時點重現**：任何一次估值都可以用當時的數據批次、規則版本與程式庫版本重算出相同結果。
