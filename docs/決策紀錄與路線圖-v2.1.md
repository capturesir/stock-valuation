### D3 的理由與影響

- API 與背景 worker 同時寫入、多台裝置同時使用時，PostgreSQL 不會出現 SQLite 的鎖檔問題；`pg_dump` 備份成熟。
- 開發、測試與正式環境用同一種資料庫，才不會出現只在某一種資料庫發生的錯誤。2.0.0-alpha.1 已有一例：SQLite 不保存時區，舊紀錄的時間因此多了 8 小時（已在 `e2afb69` 修正）。
- 影響：本機開發需要一個 PostgreSQL（`docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d db redis`，或自行安裝 PostgreSQL 16）。後端測試每次建立臨時資料庫，GitHub Actions 加 PostgreSQL 服務容器。

## 2. 兩個核心價值

> **其一：財報數據準確。** 由資料來源到後續處理，全部按投資界標準與最高標準進行，確保數據準確、處理正確；AI 的作用排在這之後。
>
> **其二：財報自動整理、歸類並統一呈現。** 財報頁要方便比較，並能在財報上做更多分析；系統日後可陸續加入分析功能。
>
> **另外：** 系統要把股票市場數據與財報數據持續收集、累積起來。

這兩點決定了所有取捨：**數據層先於 AI 層，正確先於方便。** 下文第 3、4 節是它們的具體做法。

## 3. 財報數據標準

### 3.1 現況（2.0.0-alpha.1，以程式碼為準）

| 項目 | 現況 | 問題 |
| --- | --- | --- |
| 財報來源 | 只有 Yahoo（`src/fetch/yahoo.py` 經 yfinance） | 非官方介面；Yahoo 已自行歸類，看不到原始科目；只有約 4–5 年；數字會被靜默重編 |
| SEC | `src/fetch/sec.py` 只抓申報清單；CIK 對照寫死 3 隻股票 | 沒有使用官方 XBRL 數據 |
| 披露易 | `src/fetch/hkex.py` 只搜尋公告標題 | 沒有財報數字 |
| 保存 | 每次覆寫 `cases/<代號>/yahoo_fundamentals.json` | 沒有歷史、無法追溯某次估值當時用的數字 |
| 每個數字的出處 | 只有整份 Yahoo 頁面的網址 | 無法追到申報文件、科目與期間 |
| 檢查 | 引擎有勾稽，但沒有對財報本身做系統性檢查 | 錯誤數據會直接進入估值 |

### 3.2 四層架構

每個數字都能由財報頁一路追回原始文件。

```
① 原始層   原樣保存每次抓取的內容（JSON、XBRL、HTML、PDF），附來源網址、抓取時間、SHA-256，永不修改
      ↓
② 申報層   逐個數字拆出「申報原值」：公司、原始科目（例如 us-gaap:Revenues）、數值、單位、
           倍數、貨幣、期間起訖、時點或期間、財年／季度、申報類型、文件編號、申報日、分部維度
      ↓
③ 標準層   按「標準科目表」歸類：每個標準值記錄用了哪些申報值、哪條規則（血統 lineage）
      ↓
④ 檢查層   對③逐期執行檢查規則，結果存檔並在財報頁顯示；未通過的期間不會靜默進入估值
```

### 3.3 資料來源與優先次序

| 市場 | 主來源 | 第二來源（交叉核對） | 說明 |
| --- | --- | --- | --- |
| 美股 | **SEC XBRL**：`companyfacts`、`submissions`；以 `company_tickers.json` 取得所有代號的 CIK | Yahoo | 官方、免費、有十多年歷史。SEC 要求 User-Agent 附聯絡方式，由管理員在設定中填寫；請求速率限制在每秒 10 次以內 |
| 港股 | **免費來源先行（D11）**：Yahoo 加年報 PDF 抽取，逐項交叉核對 | Yahoo | 披露易沒有免費的結構化財報數據。付費數據商（第 3.8 節，例如 GuruFocus）日後經「數據來源介面」接入，用戶自備金鑰 |
| 其他市場 | Yahoo | — | 標示為「單一非官方來源」，信心等級較低 |

所有來源經統一的「數據來源介面」接入（與 D4 的新聞來源介面同一設計），日後加入新來源不需要改動上層。

### 3.4 標準科目表

- 參照 US GAAP 與 IFRS 分類法（taxonomy），以及主流數據商的標準化做法，自訂一套「SV 標準科目」，每個科目有代碼、中英文名稱、正負號慣例、所屬報表與小計關係。
- **按行業分模板**：一般企業、銀行、保險各一套（銀行沒有「營收」與「毛利」，而是淨利息收入、撥備等）。這也是 D5 的 DDM／RI 所需的數據基礎。
- 對照規則（mapping）以設定檔維護，可版本化並有測試：每個標準科目列出原始科目的優先次序，或由其他科目計算。
- 財報頁可在「標準化」與「申報原貌」之間切換。

### 3.5 期間與股數處理

- **Q4 推算**：10-K 沒有單獨的第四季，Q4 等於全年減首三季，並標示「推算」。
- **年初至今拆分**：10-Q 的現金流量表是年初至今的累計數，要拆成單季。
- **TTM**：以最近四個單季加總；資產負債表取期末值。
- **財年對齊**：保留公司自己的財年，另提供曆年對齊視圖；處理 52／53 週財年。
- **股數**：分開保存期末股數、加權平均股數（基本、攤薄）；拆股、合股後按投資界慣例追溯調整每股數據，並保留未調整原值。
- **單位與貨幣**：統一換成「百萬、申報貨幣」，換算由程式完成並記錄原始單位；跨貨幣比較時才按當日匯率換算。

### 3.6 檢查規則（每期執行，附嚴重程度）

| 類別 | 例子 | 容許誤差（預設） |
| --- | --- | --- |
| 勾稽 | 資產 ＝ 負債 ＋ 權益；毛利 ＝ 營收 − 銷售成本；各小計等於明細加總 | 0.5% |
| 報表互連 | 損益表淨利 ＝ 現金流量表起點淨利；期初現金 ＋ 淨變動 ＋ 匯率影響 ＝ 期末現金 | 0.5% |
| 每股 | EPS ≈ 歸屬股東淨利 ÷ 加權平均股數 | 2% |
| 單位與正負號 | 數字突然大 1,000 倍；費用出現正數 | — |
| 期間連續 | 缺季、重複期間、期間長度異常 | — |
| 跨來源 | SEC 與 Yahoo 同一科目相差超過門檻 | 1% |
| 重編 | 同一期間在較新的申報中數字改變：保留兩個版本，標示重編日期 | — |
| 異常變動 | 按年變動超過行業常態，只提示不阻擋 | — |

- 每家公司每期得出「數據品質」等級，在財報頁與估值頁顯示。
- 「錯誤」級別的檢查未通過時，該期數據不會自動用於估值；用戶可以覆核並沿用 v1.1 的調整留痕機制（R04–R07）處理。
- **AI 在這之後才登場**：v2 計劃的 T1（財報異常偵測）以檢查層的結果作為輸入，負責解釋與提出調整建議，不負責判斷數字對錯。

### 3.7 時點正確（point-in-time）

每個數字都保存「申報日」與「抓取時間」。每次估值記錄當時用的是哪一批數據；回看舊估值或做回測時，只會用當時已公布的數字，不會混入事後的重編。

### 3.8 付費數據商候選（D11）

以下只是候選名單，**價格、覆蓋範圍與授權條款以各服務商官方資料為準**，接入前須實測。

| 層級 | 服務商 | 特點 | 注意 |
| --- | --- | --- | --- |
| 個人／小團隊 | GuruFocus | 長年期財報（官方稱約 30 年）、全球市場、有 API 訂閱 | 需確認港股覆蓋年期與 API 每日上限 |
| 個人／小團隊 | Financial Modeling Prep（FMP） | REST API、全球財報、美股有「申報原貌」數據，價格較低 | 港股數據的標準化方式需實測 |
| 個人／小團隊 | EOD Historical Data（EODHD） | 財報與每日價格一站式、覆蓋多個交易所（含港股） | 同上 |
| 機構級 | LSEG（Refinitiv）、S&P Capital IQ、FactSet、Morningstar、Bloomberg | 標準化與時點數據最完整，投資界常用 | 費用高；多為按席位授權 |
| 大中華 | Wind 萬得、東方財富 Choice、同花順 iFinD | 港股與 A 股覆蓋深，大中華機構常用 | 授權與海外使用條件需確認 |

**評估方法（接入前必做）：**

1. 抽 10–20 隻港股（含銀行、保險、地產、內地企業），把服務商的數字與年報原文逐項比對，套用 §3.6 的檢查規則。
2. 檢查覆蓋年期、季度數據、重編處理（申報原值或重編後數值）、是否有申報日（時點正確所需）。
3. **授權條款**：本系統會把數據保存累積並供多用戶使用（D6、D10），不少服務商禁止長期保存或多人共用，必須先確認。
4. API 速率與費用是否足以支持每日更新。

## 4. 市場數據累積

| 數據 | 內容 | 來源 | 頻率 |
| --- | --- | --- | --- |
| 證券主檔 | 代號、交易所、交易貨幣、名稱、行業分類、上市日 | Yahoo、SEC、披露易 | 首次使用時建立，每週更新 |
| 每日價格 | 開高低收、成交量、未調整收市價 | Yahoo | 每個交易日收市後 |
| 公司行動 | 派息（除淨日、金額）、拆股與合股 | Yahoo，美股以 SEC 核對 | 每日 |
| 調整後價格 | 由系統以未調整價格加公司行動自行計算總回報；並與 Yahoo 的調整價核對 | 系統計算 | 每日 |
| 匯率 | 每日收市匯率（顯示貨幣換算用） | Yahoo | 每日 |
| 無風險利率 | 美國、香港 10 年期等 | 現有 `src/fetch/rf.py` | 每日 |

- **首次使用即回補**：任何代號第一次出現（觀察名單、估值、組合、比較），就回補全部可取得的歷史。
- **每日排程**：港股約 16:30（香港時間）、美股約 17:00（紐約時間）收市後更新；範圍是所有曾經使用過的代號。
- **不遺失**：價格以**未調整**數字保存（日後拆股也不會改變已保存的數字）；來源日後修正某天的數字時，舊值寫入修訂紀錄（`price_revisions`）再更新，任何時候都追溯得到。
- **當日收市後才保存當日價格**，避免把盤中價當成收市價。
- **總回報自行計算並與來源核對**：首次回補時把系統計算的總回報與來源的調整後價格逐日比較，差距超過 0.1% 即標示警示。實測（2026-11-18）：NVDA、SPY、BRK-B、2800.HK、USDHKD 差距 ≤ 0.0001%；**0005.HK（匯豐）差 30%**，原因是 Yahoo 的派息欄已換算為港元，但其調整後價格卻用美元派息金額計算，每次派息少算約 0.6%。系統的計算是正確的一方，這正是需要獨立核對的例子。
- 匯率也是「證券」（例如 `USDHKD=X`），用同一套方法累積；每日更新會為所有用到的貨幣建立兌美元與兌港元的匯率。
- 投資組合最佳化、走勢比較、估值走勢圖與觀察名單提醒，全部讀這份累積數據，不再即時向 Yahoo 抓取。

## 5. 新需求

### 5.1 多用戶與角色（D6）

| 角色 | 可以做的事 |
| --- | --- |
| 管理員 | 管理用戶（新增、停用、重設密碼、指派角色）、品牌設定、全系統設定（數據來源、SEC 聯絡資料、AI 價格表、排程） |
| 一般用戶 | 自己的觀察名單、投資組合、比較組合、顯示貨幣與介面設定；執行估值 |

- 網頁登入用 httpOnly Cookie 工作階段；App 與小程序用存取令牌。密碼以 Argon2 雜湊保存；登入失敗次數限制。
- 現有的單一 `APP_API_TOKEN` 改為機器對機器用途（例如排程或外部腳本）。
- 第一次啟動時以指令建立第一個管理員帳號。
- **共享與私人**：市場數據、財報數據與估值紀錄屬全系統共享（D10）；觀察名單、投資組合、比較組合與個人設定屬各用戶私人。AI 金鑰、預算與價格表屬全系統設定，只有管理員可以修改（D9）。

### 5.2 品牌設定

- 管理員可設定：系統名稱、Logo（淺色與深色主題各一，SVG 或 PNG，上限 512 KB）。
- 套用到：頁首、瀏覽器分頁標題、登入頁、PWA 圖示與名稱、Excel 與報告的頁首。
  （已完成。Excel 與報告在估值完成時寫入當時的名稱與 Logo；Excel 只能嵌入 PNG Logo，SVG Logo 只顯示名稱。）
- PWA 的 manifest 目前在建置時寫死，改為由後端動態產生；圖示由上傳的 Logo 自動產生各種尺寸。
- Logo 檔案保存在資料卷（不進版本控制），資料庫只記路徑與雜湊。

### 5.3 投資組合最佳化

| 項目 | 規格 |
| --- | --- |
| 資產 | 最多 10 個代號；自動轉換格式（`2800` → `2800.HK`、`BRK.B` → `BRK-B`） |
| 回測期間 | 近一年、兩年、三年、五年、十年、今年至今、自訂起訖；可用期間受最短歷史的資產限制，並會提示 |
| 價格 | 含股息的總回報（第 4 節的調整後價格）；港美股假期不同，先對齊交易日 |
| 貨幣 | 按用戶的顯示貨幣換算（D7） |
| 再平衡 | 不再平衡（預設）、每月、每季、每年（D8） |
| 約束 | 只做多、權重合計 100%、每項資產可設上下限（例如 TQQQ 最多 20%）、權重以 1% 為單位 |
| 得分條件 | Sharpe、最大回撤、回報率；可單選，或設權重組成綜合得分（各指標先標準化） |
| 演算法 | 隨機抽樣數萬個組合，再以局部最佳化（SLSQP）精修；固定隨機種子，結果可重現 |
| 輸出 | 最佳比例、各指標、得分明細、前幾名候選組合、效率前緣圖 |
| 保存 | 組合與「場景」一併保存：輸入、實際使用的數據期間、數據版本、參數、隨機種子、得分明細、系統版本、時間 |
| 防過度擬合 | 樣本外檢驗：以前段期間最佳化、後段期間驗證，並排顯示兩段的表現 |

### 5.4 走勢比較圖

- 最多 10 條線，可以是股票，也可以是已保存的投資組合；指定其中一條做 benchmark。
- 預設起點統一為 100；也可切換為回報百分比。
- **勝負區間著色**：按設計規範，跑贏用藍、跑輸用橙。10 條線同時著色會很亂，所以只為選中的那一條著色（點擊圖例切換），另附一張「相對強弱」副圖（標的 ÷ benchmark）。
- **表格**：
  - 期間回報：1 個月、3 個月、6 個月、今年至今、1 年、3 年（年化）、5 年（年化）、自訂期間。
  - 指標：總回報、年化回報、年化波動率、Sharpe、Sortino、最大回撤、回撤持續期、Calmar、Beta、Alpha、相關系數、追蹤誤差、資訊比率、上行／下行捕獲率、跑贏 benchmark 的月份比例、最佳／最差月份。
  - 可匯出 CSV、Excel。
- 比較組合可保存。

5.3 與 5.4 共用同一個「指標計算模組」（純 Python，逐項有單元測試，公式與 CFA 協會等投資界慣例一致），估值走勢圖與觀察名單也會使用。

### 5.5 文件庫與問答（D13，2.0.0-alpha.5）

擁有者 2026-11-25 決定。每隻股票一個文件庫，股票詳細頁設對話介面，用戶可以問 AI 關於該公司的問題。

**資料來源與標示**
- 先按系統內該股票的文件庫回答；文件庫的證據不足（檢索分數低於門檻）或問題涉及最新申報之後的事，才上網搜尋。
- 每句答案標明來源：「文件庫」附申報、章節與原文連結；「網上」附網址與抓取日期。抓到的網頁存入文件庫（標記為網上來源），日後可再引用。
- 數字問題（例如近五年毛利率）由 AI 呼叫工具讀標準層，數字精確、可追回申報文件，不靠文字檢索。
- 沒有證據時明確回答「文件庫沒有相關資料」，不憑模型記憶作答。
- 文件與網頁內容只當資料，不當指令（防提示注入）；對話紀錄屬用戶私人。

**不超過模型上下文限制**：文件庫大小不限，每次提問有預算。
- 入庫時按章節切段（每段約 500 字詞），附元數據（股票、申報、日期、章節、頁碼、連結）。
- 每次只取最相關的 8–12 段（混合檢索：PostgreSQL 全文搜尋＋pgvector 向量，再重排），連同問題約 6–10k tokens。
- 長對話把舊內容壓縮為摘要；跨年份的大問題先用入庫時預先做好的「每份申報摘要、每章摘要」（分層摘要），再逐份深入。

**小型模型**
- 檢索負責找證據，7B–14B 的模型（8k–32k 上下文）足以做「根據段落回答並註明出處」，可在本機或便宜的雲端執行；向量與重排模型（例如 bge-m3、bge-reranker）可用 CPU。
- 小型模型較弱的多步推理與計算交給工具；複雜問題可升級到大型模型，對應現有的 AI 模式（輕量／標準／深度）。

**步驟**

| 步驟 | 內容 |
| --- | --- |
| 1 | 文件入庫：SEC 申報正文（10-K、10-Q、8-K）、港股年報 PDF；轉文字並按章節切段 |
| 2 | 索引：全文搜尋與向量（pgvector），重排；每份申報與每章的摘要 |
| 3 | 問答接口：附出處的回答、數字工具（讀標準層）、證據不足時拒答；小型模型可用 |
| 4 | 上網補充：只在文件庫不足時使用，標示來源，抓取內容入庫 |
| 5 | 股票頁對話介面：問答、出處連結、來源標示、對話紀錄（私人） |
| 6 | 準確度測試集：出處正確率、拒答正確率，小型與大型模型分別記錄 |

- 框架已完成（2.0.0-alpha.1）：共用字典 `@sv/i18n`（繁體中文、简体中文、English），CI 檢查三種語言的詞條與佔位符完全一致，缺一條即不能合併。
- 網頁所有介面文字都經字典；後端錯誤一律附固定代碼並按 `Accept-Language` 回覆；用戶的語言選擇保存在帳號。
- **規則**：新功能的文字一律加入三種語言的字典；後端給用戶看的訊息一律用代碼（`AppError`），不寫死中文。
- **未完成**：v1 引擎產生的文字（資料缺口、Excel、估值報告）仍只有繁體中文，排在 alpha.3 與引擎改造一起處理。

## 8. 文件維護規則（擁有者決定，2026-11-18）

每次更新，同一個 PR 都要一併更新以下文件（內容受影響時）：

| 文件 | 內容 |
| --- | --- |
| `docs/決策紀錄與路線圖-v2.1.md`（本文件） | 新決定、路線圖進度 |
| `CHANGELOG.md` | 更新日誌，寫在「未發布」一節 |
| `docs/資料庫設計.md` | 資料表、欄位、索引、遷移 |
| `docs/接口文件.md` | `/api/v1` 各接口的用途、權限、格式 |
| `README.md`（及安裝方法有變時的 `INSTALL.md`） | GitHub 上的說明 |

資料庫設計與接口文件由 CI 測試（`backend/tests/test_docs_sync.py`）核對：漏列資料表、欄位或接口，或列了已不存在的項目，PR 都不能合併。

**系統功能及操作說明書（圖文教學）**留待系統開發完成後才製作，開發期間不逐次更新。
