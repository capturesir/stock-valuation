# 接口文件（API）

- 適用版本：2.0.0-alpha.3 開發中
- 基本路徑：`/api/v1`
- 機讀合約：執行中的系統提供 OpenAPI 3.1（`/api/v1/openapi.json`）與互動文件（`/api/v1/docs`）。各欄位的完整型別以 OpenAPI 為準；本文件說明每個接口的用途、權限與要點。
- 以程式碼為準：路由在 `backend/app/routers/`，資料格式在 `backend/app/schemas.py`。本文件漏列任何接口，CI 的 `backend/tests/test_docs_sync.py` 會失敗。
- **維護規則**：每次新增、刪除或修改接口，都要同一個 PR 更新本文件。

## 1. 共同規則

### 1.1 登入與權限

| 方式 | 用於 | 做法 |
| --- | --- | --- |
| Cookie | 網頁 | `POST /auth/login` 設定 `sv_session`（HttpOnly、SameSite=Lax，30 天） |
| Bearer 令牌 | App、小程序 | `POST /auth/login` 帶 `issue_token: true`，之後每個請求加 `Authorization: Bearer <令牌>` |
| 查詢參數 | SSE 串流 | 瀏覽器的 EventSource 不能加標頭，可用 `?access_token=<令牌>` |
| 機器令牌 | 腳本、整合 | 環境變數 `APP_API_TOKEN` 的值作為 Bearer 令牌；具管理員權限，但不代表任何用戶，不能用個人接口（觀察名單、個人帳號） |

權限分三級，下表「權限」欄使用：

- **公開**：不需登入。
- **登入**：任何已登入的用戶（`admin` 或 `member`）。
- **管理員**：只限 `admin`（決策 D6）。

連續登入失敗會鎖定帳號 15 分鐘。更改密碼後，該用戶其他裝置的登入狀態失效。

### 1.2 語言

錯誤訊息按 `Accept-Language` 回覆繁體中文、简体中文或 English（zh-TW／HK／MO → 繁體；zh-CN／SG → 简体；en → English；其他 → 繁體）。

### 1.3 錯誤格式

所有錯誤都附固定代碼，前端按代碼翻譯，不依賴文字：

```json
{ "detail": { "code": "invalid_ticker", "error": "代號「…」格式不正確" } }
```

| HTTP | 何時 | 常見代碼 |
| --- | --- | --- |
| 400 | 輸入有誤 | `invalid_ticker`、`optimize_bounds`、`optimize_duplicate`、`optimize_too_short`、`compare_benchmark`、`portfolio_not_found`、`no_common_dates`、`no_prices`、`bad_date`、`wrong_password`、`brand_name_length`、`sec_contact_missing`、`sec_organisation_invalid`、`email_invalid`、`sec_not_filer`、`bad_request` |
| 401 | 未登入或登入已過期 | `login_required` |
| 403 | 權限不足 | `admin_required`、`user_required`（機器令牌用了個人接口） |
| 404 | 找不到 | 例如公司資料查無此代號；`statements_not_synced`（尚未取得申報數據） |
| 409 | 衝突 | `recent_valuation` |
| 502 | 上游數據來源無法回應 | `upstream` |
| 422 | 欄位型別不符（FastAPI 驗證） | — |
| 429 | 超過請求速率 | `rate_limited`，附 `retry_after` 秒數與 `Retry-After` 標頭 |
| 503 | 估值佇列已滿 | `queue_full`，附 `retry_after` |

### 1.4 請求速率限制

管理員可在 `PUT /admin/limits` 調整，按用戶（未登入時按 IP）計算：

| 限制 | 套用到 |
| --- | --- |
| `lookup_per_minute` | `GET /stocks/{ticker}/lookup`、`GET /stocks/{ticker}/profile` |
| `prices_per_minute` | `GET /stocks/{ticker}/prices` |
| `valuations_per_hour` | `POST /valuations` |
| `concurrent_valuations_per_user`、`queue_max` | `POST /valuations` |
| `revalue_cooldown_hours` | `POST /valuations`（近期已估值時回 409） |

### 1.5 格式慣例

- 日期 `YYYY-MM-DD`；時間 ISO 8601（UTC）。
- 金額一律附貨幣欄位（`currency`、`trading_ccy`），不假設港元或美元。
- 代號不分大小寫，系統轉為大寫並檢查格式。

### 2.7 估值工作

| 方法 | 路徑 | 權限 | 用途 | 請求 → 回應 |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/ai/plan?ticker=&mode=&tasks=` | 登入 | AI 工作清單：每項預估 Token 與費用、是否可用、略過原因（`skip_code`） | → `Plan` |

| GET | `/api/v1/jobs/{job_id}/events` | 登入 | 工作進度串流（Server-Sent Events，斷線 2 秒後重連） | → `text/event-stream` |

`POST /valuations` 的回應：

| HTTP | 意思 |
| --- | --- |
| 202 | 已建立新工作 |
| 200 | 同一代號已在估值，加入該工作（`joined: true`） |
| 409 | 近期已用相同條件估值（`recent_valuation`）；帶 `force: true` 重算 |
| 429 | 超過每小時估值次數或同時估值數 |
| 503 | 佇列已滿（`queue_full`） |

估值一次只執行一個（v1 引擎寫入共用資料夾），其餘排隊，`Job.queue_position` 顯示位置。

| GET | `/api/v1/stocks/{ticker}/filed-concepts` | 登入 | 申報原貌：公司申報過的全部科目，附單位、筆數、最早與最新期間；`source=instance` 為公司自訂科目（來自年報 XBRL instance，排在 companyfacts 科目之後） | → `FiledConceptOut[]` |
| GET | `/api/v1/stocks/{ticker}/filed-facts?concept=&taxonomy=&unit=&limit=` | 登入 | 一個科目的每個申報數字，最新期間在前；`taxonomy` 為公司前綴（例如 `nvda`）時讀公司自訂科目（`source=instance`，`fy`／`fp`／`frame` 為空）；重編時同一期間有多筆（每份申報一筆）；附 SEC 申報索引頁與主文件連結 | → `FiledFactOut[]` |

| GET | `/api/v1/stocks/{ticker}/statements?period=&view=&as_of=&years=&plan=` | 登入 | 標準化財報：每個標準科目、每個期間的數字與出處（規則、申報科目、申報文件、重編、公式、推算、股份分拆調整）。`period=annual`（預設，財年）或 `quarterly`（財季）；有連續四季時最前一欄是近十二個月（TTM）。`view=latest`（預設，每個期間用最新申報，含重編）或 `original`（首次公布）；`as_of` 只用當日或之前申報的數字；`years` 1–40 個期間，預設 10（季度至少 12），最新在前。附 `ratios`：比率（每格附計算用的數值）、按年增長、3 年與 5 年複合增長。附 `checks`：檢查規則版本、各期品質等級（A／B／C）、各期通過／失敗／略過數目、所有失敗的檢查（比較的數字與差異）、交叉核對用的 Yahoo 數字取得時間。附 `share_classes`（只限年度）：按股份類別的每股盈利（`member`、`label`、`item`，每格附申報原值、分拆系數與 SEC 連結）。有公司覆蓋規則時 `ruleset_version` 為 `<版本>+<CIK>.<覆蓋版本>`。`plan`（D12）：`auto`（預設：我的個人方案 → 中央方案 → 不調整）、`central`、`personal`、`none`；回應的 `plan` 為套用的方案與版本，調整過的格有 `adjusted_from`（調整前的標準值）與 `adjustment`（直接調整：`reason`、`basis`、`by`、`at`；隨調整重算：`from`）；`adjustments_not_shown` 列出不在顯示期間的調整；檢查仍按未調整的標準層 | → `StandardStatements`；404 `statements_not_synced` |

| GET | `/api/v1/stocks/{ticker}/statements/export?format=&period=&view=&years=&plan=` | 登入 | 匯出標準化財報（按 `plan` 套用調整方案，出處工作表列出每項調整的原值與理由）。`format=xlsx`（預設）為 Excel：財報、比率與增長（含複合增長）、出處（每格的規則、科目、申報、原文連結）、檢查四個工作表，附系統名稱與 Logo；`format=csv` 為一張表（財報、比率、增長），UTF-8 附 BOM。數值為精確原值（不是百萬）；項目名稱按 `Accept-Language` | → xlsx／csv 檔案；404 `statements_not_synced` |
| GET | `/api/v1/stocks/{ticker}/adjustment-plans` | 登入 | 調整方案（D12）：中央方案與我的個人方案（目前版本的全部調整、全部版本清單），以及中央方案是否在我複製或最後合併後有新版本（`central_updated`） | → `AdjustmentPlansOut` |
| GET | `/api/v1/adjustment-plans/{plan_id}/versions/{version}` | 登入 | 方案的某一版本的全部調整；中央方案所有人可看，個人方案只限本人 | → `AdjustmentVersionOut`；404 `plan_not_found` |
| PUT | `/api/v1/stocks/{ticker}/adjustment-plans/central` | 管理員 | 保存中央方案的新版本：`adjustments` 為完整一套（項目、期間、數值、理由、依據），`base_version` 為編輯時依據的版本（新方案 0） | → `AdjustmentPlansOut`；400 `adjustment_invalid`、`adjustments_too_many`；409 `plan_conflict` |
| PUT | `/api/v1/stocks/{ticker}/adjustment-plans/personal` | 登入 | 保存我的個人方案的新版本；第一次保存即建立並記錄當時的中央方案版本；`central_version` 記錄已合併（或已查看）的中央方案版本 | → `AdjustmentPlansOut`；400／409 同上 |

`FiledFactOut.value` 是精確十進位字串（例如 `"2.94"`、`"130497000000"`），不經浮點數；前端顯示時才換算。

## 3. 計劃中的接口（alpha.3 起）

落實時移入第 2 節：

- 財報（alpha.3）：維度數據與公司自訂科目、調整方案（D12）；調整方案（D12）的中央方案與個人方案、版本紀錄。
