# 股票估值系統改進計劃 v2.0

- 日期：2026-11-17（澳門時間）
- 對象：`capturesir/stock-valuation` v1.1.1
- 範圍：AI 分析能力、多方法合理股價、估值走勢圖、財報資料保留、介面精簡、自帶 AI 金鑰與費用中心
- 原則不變：**理論價永遠由本機 Python 引擎計算**；AI 只負責閱讀、整理、提案與解釋，所有 AI 產出都要有來源、經驗證、可由用戶否決。

---

## 0. 一頁摘要

| 方向 | 現況（v1.1） | 目標（v2.0） |
| --- | --- | --- |
| AI 角色 | 實際只送公司名稱與行業給 AI；輸出「存檔備查」，不影響估值；投行對照步驟從未被呼叫 | 8 個有實際作用的 AI 任務：財報異常偵測、新資訊摘要、假設提案附理由、反方審查、報告撰寫等，全部輸出結構化 JSON 並附來源 |
| 估值方法 | 只有 FCFF DCF（五情境）；銀行、保險也被套用 FCFF | 依行業自動選方法：DCF、反向 DCF、相對估值、DDM／剩餘收益（金融業）、SOTP；可加權得出綜合理論價 |
| 走勢圖 | 每次估值一個點，只畫基準理論價 | 每日市價線＋各方法理論價階梯線＋悲觀–樂觀區間帶＋財報／公告事件標記＋兩次估值的「變動歸因」 |
| 財報資料 | 每次覆寫 `cases/<代號>/yahoo_fundamentals.json`，只有 Yahoo 約 4–5 年 | 每次抓取都保存快照，累積超過 4 年，看得到重編差異；美股加入 SEC XBRL 官方資料 |
| 介面 | 結果以 7 張 Excel 分頁呈現，走勢圖只在第一頁、AI 用量只在最後一頁 | 以股票為中心的 5 個分頁：總覽、估值、財報、新資訊、紀錄；Excel 原貌保留為「Excel 檢視」 |
| AI 費用 | 估值後只顯示 Token 數，沒有金額、沒有預算 | 開跑前按任務列出預估 Token 與費用範圍、可逐項勾選；執行中逐項打勾並累計費用；設定每次／每月上限；用量儀表板 |

## 1. 現況診斷（以程式碼為準）

### 1.1 AI 實際上做了甚麼

| 位置 | 宣稱 | 實際 |
| --- | --- | --- |
| `orchestrator.py` 的 `ai_extract` 步驟 | 「AI 正在讀取財報摘要」 | 只傳送 `longName/industry/sector/country/fullTimeEmployees`，沒有任何財報數字；結果寫進 `llm_status` 後不再使用 |
| `research.ai_plan()` 的工作預覽 | 「輸入為 N 個已收集財報科目的摘要」 | 同上，並沒有送出財報科目，**預覽與實際不符** |
| `research.ai_plan()` 的「AI 對照投行目標價」 | 「併入上述請求」 | `llm_steps.ib_compare()` 在整個程式碼中從未被呼叫 |
| `generic_spec._propose_paths()` | AI 提出增長與利潤率 | 有效，但只用於通用規格；首年差距超過 12pp／10pp 即被整體拒絕，理由欄位只有一句話，沒有引用新資訊 |
| `prompts/propose_assumptions.md` | 要求 AI 輸出 capex、ΔNWC、RONIC、CRP、Kd 等 | 程式只取 `revenue_growth`、`ebit_margins`、`terminal_g`，其餘欄位被丟棄，等於浪費輸出 Token |

**結論：** 用戶付了 AI 費用，但除了通用規格的增長路徑之外，估值結果與不用 AI 幾乎相同。v2.0 的第一件事是讓 AI 名副其實，並且令預覽與實際一致（P0）。

### 1.2 其他與本計劃相關的發現

- **金融業方法不適用：** `generic_spec.INDUSTRY_MAP` 把 `banks - diversified`、`insurance - property & casualty` 對應到 Damodaran 行業後，仍以 FCFF 估值。對銀行而言，債務是原材料而不是融資，FCFF 與 WACC 的定義都失效。
- **走勢圖幣別標示：** `runlog.record_from_calc()` 記錄的 `currency` 是模型貨幣（例如 0883.HK 為 CNY），但 `fair_value` 是交易貨幣（HKD），圖表標示會錯。
- **財報不保留歷史：** 每次估值覆寫 `cases/<代號>/yahoo_fundamentals.json`；Yahoo 只提供約 4–5 期年報，而且會被重編，過往的數字無從追溯。
- **測試基準與執行輸出共用目錄：** `out/`、`cases/` 同時是測試基準與真實輸出，跑過一次估值後測試就失敗（README 亦有提及）。
- **本機服務防護：** 網頁綁定 `127.0.0.1`，但沒有 Host 標頭檢查。惡意網頁可透過 DNS rebinding 呼叫 `/api/settings/llm`，把 API 位址改成攻擊者的伺服器，下次估值時金鑰就會被送出。
- **命令列 `--date` 預設寫死為 `2026-11-11`**（由測試鎖定），不加 `--date` 時會覆寫舊資料夾。

## 2. 設計原則

1. **引擎算數，AI 讀書：** AI 不輸出每股理論價、WACC 或任何最終數字；它輸出「調整建議」「假設路徑」「事件影響」，由引擎計算，由驗證器檢查。
2. **每個 AI 數字都要有出處：** 送給 AI 的每段資料都有 `source_id`；AI 引用的 `source_id` 若不在本次輸入之內，該項即被拒絕。
3. **人在迴圈中：** 財報調整與假設變更預設是「建議」，用戶按「採用」後才進入模型，並沿用 v1.1 的調整留痕機制（R04–R07）。
4. **先算錢，再花錢：** 開跑前顯示預估費用，超出用戶設定的上限就不執行；執行後以服務商回報的用量計算實際費用。
5. **沒有新資訊就不花錢：** AI 結果以輸入雜湊快取；只有市價改變時重估不呼叫 AI。
6. **不用 AI 也完整可用：** 所有 AI 任務都有規則後備，結果標示 `rules_fallback`（保留現有行為）。

## 3. AI 能力提升：任務目錄

### 3.1 八個 AI 任務

| # | 任務 | 輸入（全部由程式擷取） | AI 輸出（JSON） | 用戶把關 | 觸發時機 |
| --- | --- | --- | --- | --- | --- |
| T1 | **財報異常偵測與調整建議** | 4–5 期三大報表（約 180 科目）、會計政策摘要、與上次快照的差異 | 可疑項目清單：一次性損益、重編、單位錯誤、IFRS 16 租賃、已終止業務、股數異常；每項附建議調整值、方向、理由、`source_id` | 每項「採用／忽略」；採用後寫入 `adjustments.json` | 新財報、首次估值 |
| T2 | **新資訊摘要與影響評估** | 最新 10-Q／10-K／8-K、披露易公告、業績會逐字稿、新聞標題（各附 URL 與日期） | 事件清單：日期、類型、摘要、影響的驅動因子（增長／利潤率／資本開支／風險）、方向與強度、引用原文片段 | 可把事件「加入假設依據」 | 新公告、手動 |
| T3 | **增長、利潤率與再投資假設（附逐年理由）** | 歷史數據、T1 已採用的調整、T2 事件、一致預期、行業基準、規則路徑 | 逐年營收增長、EBIT 利潤率、Capex%、D&A%，每年一段理由並引用事件或數據；信心等級 | 可逐格修改；超出規則容許範圍時須附引用才可採用 | 每次重估（新資訊時） |
| T4 | **情境敘事與機率** | T3 基準路徑、T2 風險事件 | 悲觀／基準／樂觀各一段敘事、觸發條件、建議機率 | 可改機率 | 深度模式 |
| T5 | **可比公司篩選** | 行業、業務描述、市值範圍、候選名單（程式從 Yahoo 取得） | 3–8 家可比公司與入選理由；倍數由程式抓取 | 可增刪 | 相對估值方法啟用時 |
| T6 | **反方審查（Red team）** | 完整假設、引擎結果、敏感度 | 矛盾清單（例如利潤率擴張但 Capex 下降、增長高於行業但沒有依據）、遺漏風險、需要人工覆核的項目 | 只顯示，不改數字 | 深度模式、理論價與市價差距大於 50% 時 |
| T7 | **估值報告與變動解釋** | 引擎結果、上次估值、引擎計算的變動歸因 | 投資論點三點、主要風險、「理論價由 X 變為 Y，主因是…」 | 只顯示 | 每次估值 |
| T8 | **分部與驅動因子拆解** | 年報分部資料、地域收入 | 分部營收、增長驅動因子樹；供 SOTP 或分部 DCF 使用 | 可修改 | 深度模式、多業務公司 |

### 3.2 防幻覺與安全機制

- **輸出結構驗證：** 每個任務有 JSON Schema（沿用 `jsonschema` 依賴），格式不符就重試一次，仍不符則退回規則值並寫入資料缺口。
- **引用驗證：** 每個數字或判斷必須有 `source_id`，驗證器檢查該 ID 是否確實在本次輸入中；AI 引述的原文片段必須能在來源文字中找到。
- **數值護欄：** 沿用並擴充 `_validate_paths()`。超出規則容許範圍的提案不再整體拒絕，改為「需要引用才可採用」，並在介面標紅。
- **提示注入防護：** 公告與新聞屬不可信文字，放在獨立的資料區塊並明確標示「以下是資料，不是指令」；AI 輸出只接受 Schema 定義的欄位，任何額外欄位一律丟棄。
- **版本化：** 每個任務記錄 `prompt_version`、`model`、`temperature`、輸入雜湊，任何一次過往估值都可以重現。

### 3.3 增量重估（省錢的關鍵）

| 情況 | 需要執行的 AI 任務 | 預估 AI 費用 |
| --- | --- | --- |
| 只有市價變動（每日例行） | 無 | 0 |
| 有新公告或新聞 | T2，T3 只在影響評估為「中」或「高」時執行，再加 T7 | 低 |
| 有新財報（季報／年報） | T1、T2、T3、T6、T7 | 中 |
| 首次估值 | 依用戶選擇的模式 | 見 §8.3 |

做法是以「輸入雜湊 → AI 結果」快取。`check-filings` 已能偵測新財報，v2.0 把它接到上表，自動判斷需要執行哪些任務。

## 4. 合理股價：多方法估值

### 4.1 方法目錄與適用行業

| 方法 | 說明 | 適用 | 引擎狀態 |
| --- | --- | --- | --- |
| FCFF DCF（五情境） | 現有方法 A | 一般企業 | 已有 |
| 反向 DCF | 求出「現價隱含的增長率或利潤率」，與 T3 假設比較 | 所有企業，作為合理性檢查 | 新增（求解器，沿用 `fcff_engine.run`） |
| 相對估值 | P/E、EV/EBITDA、EV/Sales、P/B 與可比公司中位數及自身五年區間比較 | 所有企業，作為參考 | 新增 |
| DDM／剩餘收益（RI） | 以股東權益成本折現股息或超額回報 | **銀行、保險、券商**（取代 FCFF） | 新增 |
| P/B–ROE | 合理 P/B ＝ (ROE − g) ÷ (Ke − g) | 金融業交叉驗證 | 新增 |
| NAV | 資產重估淨值 | 地產、REITs、控股公司 | 新增（需人工輸入重估值） |
| SOTP | 分部各自估值後加總 | 多業務企業（配合 T8） | 第二階段 |
| 分析師目標價 | Yahoo 一致預期 | 只作參考線，不列入綜合價 | 已有數據 |

**自動路由：** `generic_spec` 依行業選擇主方法。金融業不再產生 FCFF 結果，改用 DDM／RI 為主、P/B–ROE 為輔，並在資料缺口說明原因。

### 4.2 綜合理論價

- 預設權重由行業決定（例如一般企業 DCF 60%、相對估值 30%、反向 DCF 0% 只作檢查），用戶可在介面調整，**權重隨該次估值一併保存**。
- 顯示「足球場圖」（football field）：每個方法一條橫棒，顯示悲觀至樂觀的範圍，加上現價豎線與綜合理論價豎線。
- 情境機率（T4）可選擇性地套用為機率加權理論價，並與等權結果並列顯示。

## 5. 估值走勢圖

### 5.1 圖表設計

```
價格 (HKD)
  │            ┌────── DCF 基準（階梯線：每次估值後維持到下一次）
60├─────┐      │   ░░░░ 悲觀–樂觀區間帶（主方法）
  │     └──────┘
50├ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  相對估值（虛線）
  │   ╱╲    ╱╲╱╲___      市價（每日收市，實線）
40├──╱──╲__╱──────╲──
  │  ▲      ▲ ◆    ▲    ▲ = 財報公布   ◆ = 盈警／重大公告
  └──┴──────┴─┴────┴─────────────── 時間
       點擊任何一次估值 → 側欄顯示該次的假設、來源、變動歸因
```

- **市價**改用 Yahoo 每日收市價畫連續線，不再只有估值當天的點，看得出市價與理論價何時交錯。
- **理論價**用階梯線：一個估值在下一次估值之前都有效。
- **多方法、多結果**：每個方法一條線，可在圖例開關；同日多次估值沿用 v1.1 的 ×N 錯開標示。
- **事件標記**：財報公布、盈警、配股等標在時間軸上，解釋理論價為何跳動。
- **變動歸因**：選取兩次估值，引擎逐項替換輸入（Rf → ERP → β → 增長 → 利潤率 → 再投資 → 橋接 → 股數 → 匯率），計算每一項對理論價的貢獻，以瀑布圖顯示；T7 再用文字解釋。
- **時間範圍**：全部、近一年、近五次（沿用 v1.1）。幣別一律使用交易貨幣（修正 §1.2 所述的標示問題）。

### 5.2 資料模型

v1.1 的 `out/history/<代號>.json` 只記錄基準價與五情境。v2.0 改用單一 SQLite 檔 `data/valuation.db`（不進版本控制）。原因：多方法 × 多情境 × 多次估值 × 財報快照，用 JSON 檔查詢與合併都很吃力；SQLite 是 Python 內建、單檔、跨平台。原有 JSON 與 Excel 輸出全部保留，資料庫是附加的索引。

```sql
CREATE TABLE runs (
  run_id TEXT PRIMARY KEY, ticker TEXT, run_at TEXT, valuation_date TEXT,
  trigger TEXT,              -- manual | new_filing | news | scheduled | price_only
  filing_ref TEXT, price REAL, price_date TEXT, trading_ccy TEXT, model_ccy TEXT,
  composite_value REAL, weights_json TEXT, verify_pass INTEGER,
  ai_mode TEXT, ai_cost_usd REAL, ai_tokens_in INTEGER, ai_tokens_out INTEGER,
  inputs_hash TEXT, calc_json_path TEXT, xlsx_path TEXT
);
CREATE TABLE method_results (
  run_id TEXT, method TEXT, scenario TEXT,   -- dcf/base, dcf/bear, rel/pe, ddm/base …
  value REAL, low REAL, high REAL, weight REAL, notes TEXT
);
CREATE TABLE ai_tasks (
  run_id TEXT, task TEXT, status TEXT,        -- planned | running | done | skipped | failed | cached
  model TEXT, prompt_version TEXT, input_hash TEXT,
  est_tokens_in INTEGER, est_tokens_out INTEGER, est_cost_usd REAL,
  tokens_in INTEGER, tokens_out INTEGER, cost_usd REAL, usage_reported INTEGER,
  started_at TEXT, finished_at TEXT, output_json TEXT, error TEXT
);
CREATE TABLE statement_snapshots (
  ticker TEXT, source TEXT, fetched_at TEXT, statement TEXT,  -- is | bs | cf
  period_end TEXT, period_type TEXT, item TEXT, value REAL, currency TEXT,
  PRIMARY KEY (ticker, source, fetched_at, statement, period_end, period_type, item)
);
CREATE TABLE events (
  ticker TEXT, event_date TEXT, kind TEXT, title TEXT, url TEXT, source_id TEXT,
  ai_summary TEXT, impact_json TEXT
);
```

**遷移：** 啟動時把現有的 `out/history/*.json` 與 `out/<日期>_<代號>/` 匯入資料庫（沿用 `valuation_history()` 的去重邏輯），不刪除任何舊檔。

## 6. 財報資料保留

1. **快照而非覆寫：** 每次抓取的三大報表逐科目寫入 `statement_snapshots`，主鍵包含 `fetched_at`，所以：
   - 歷史會逐年累積，不再受 Yahoo 只有 4–5 期的限制；
   - 公司重編數字時，可並排顯示「原始公布值」與「重編後數值」；
   - 每次估值都記錄當時用的是哪一批快照（point-in-time），回看舊估值時不會混入事後才有的數據。
2. **加入官方資料源：** 美股接 SEC XBRL `companyfacts` 介面（官方、免費、有十多年歷史），與 Yahoo 交叉核對，差距超過門檻就交給 T1 標示。港股維持披露易加上 Yahoo。
3. **介面：** 「財報」分頁可選年度或季度、可選期間範圍，重編過的數字以標記顯示，滑鼠移上去可看原值與重編日期。

## 7. 介面重新設計

### 7.1 問題

- 結果以 7 張 Excel 分頁的表格呈現，閱讀者要自己在表格中找重點。
- 走勢圖只在第一頁出現，AI 用量、預測理由只在最後一頁出現，需要知道才找得到。
- 查詢區按鈕太多（估值、停止、AI 工作預覽、檢查財報、如需要則重跑、進階選項），新用戶不知道從何入手。
- 設定頁與主頁風格分離，AI 狀態在主頁看不到。

## 8. AI 金鑰與費用中心

### 8.1 自帶金鑰（BYOK）設定頁「AI 與費用」

| 區塊 | 內容 |
| --- | --- |
| 服務商預設 | 下拉選單：DeepSeek、OpenAI、Google Gemini、其他 OpenAI 相容服務、本地模型（Ollama／LM Studio，費用為 0）。選擇後自動填入 API 位址與建議模型 |
| 連線 | API 位址、模型、金鑰（只顯示長度與末四碼，沿用 v1.1）、「測試連線」，並顯示該次測試的 Token 與費用 |
| 價格表 | 每個模型的輸入、快取輸入、輸出單價（US$／百萬 Token）、查價日期、官方價目表連結；可手動修改；超過 90 天未更新時提示 |
| 預算 | 每次估值上限、每月上限、超出時的行為（停止 AI 改用規則後備，或詢問） |
| 用量儀表板 | 本月累計費用、按股票、按任務、按模型的分佈；每日費用柱狀圖；匯出 CSV |
| 隱私 | 說明哪些資料會送出（財報數字、公告文字、新聞標題），哪些不會（金鑰以外的本機設定、其他股票資料） |

**金鑰保存：** 預設沿用 `.env`（權限 0600）；可選用作業系統鑰匙圈（`keyring` 套件：macOS Keychain、Windows Credential Manager、Linux Secret Service）。金鑰永遠不送到瀏覽器。

### 8.2 預估方法

1. **輸入 Token：** 每個任務的提示詞在開跑前就由程式組裝好，所以輸入量可以精確計算：先以字元數估算（英文約每 4 字元 1 Token、中文約每字 1 Token、數字表格約每 3 字元 1 Token），再乘以該模型的**校準係數**。
2. **校準：** 每次服務商回報實際用量後，更新「實際 ÷ 預估」的移動中位數，按模型分別保存，預估會越用越準。
3. **輸出 Token：** 取該任務最近 10 次的中位數；沒有紀錄時用任務預設值，並以 `max_tokens` 作為上限。
4. **範圍：** 顯示「中位數至 P90」的範圍，加上重試緩衝（預設 15%）。推理型模型的思考 Token 按輸出計費，選用時會顯示「輸出可能多 2–5 倍」的警告。
5. **費用：** 輸入 × 輸入單價 ＋ 快取輸入 × 快取單價 ＋ 輸出 × 輸出單價。靜態指令放在提示詞最前面，以利用服務商的提示快取。

### 8.3 每次估值費用估算（示例）

以實測的 NVDA 年報資料量（約 3.4 萬字元）為基礎，各任務 Token 預算：T1 12k／2k、T2 20k／3k、T3 10k／3k、T4 6k／2k、T5 3k／1k、T6 12k／2k、T7 8k／2k、T8 25k／3k（輸入／輸出）。

| 模式 | 任務 | 輸入／輸出 Token | DeepSeek V4.1 Flash | Gemini 3.8 Flash | OpenAI GPT-6.1 Sol | 本地模型 |
| --- | --- | --- | --- | --- | --- | --- |
| 精簡 | T3、T7 | 18k／5k | ≈ US$0.011 | ≈ US$0.032 | ≈ US$0.086 | 0 |
| 標準 | T1、T2、T3、T7 | 50k／10k | ≈ US$0.027 | ≈ US$0.075 | ≈ US$0.20 | 0 |
| 深度 | 全部 8 項 | 96k／18k | ≈ US$0.050 | ≈ US$0.14 | ≈ US$0.37 | 0 |

單價取自附錄 A，未計重試緩衝與推理 Token。結論：即使用較貴的模型，一次深度估值也只是幾毛美元；真正會累積費用的是「每天對整份觀察名單重跑」，所以 §3.3 的增量重估與快取比壓低單次費用更重要。

### 8.4 執行中：工作清單、進度與費用

```
┌─ 估值進行中 0883.HK ───────────── 已用 01:12 · 預計尚餘 00:40 ─┐

│ ✔ T2 新資訊摘要     2 個高影響事件  19.2k / 2.7k     $0.0090   │
│ ◐ T3 假設提案       等待回覆…        10.1k / —        —        │
│ ○ 引擎計算與獨立驗證                                    —      │
│ ○ T7 報告與變動解釋                                     —      │
│ ─────────────────────────────────────────────────────────── │
│ 累計 US$0.0145 · 預估總額 US$0.02–0.04 · 上限 US$0.50          │
│                                         [停止（保留已完成）]    │
└──────────────────────────────────────────────────────────────┘
```

- 狀態：○ 待執行、◐ 執行中、✔ 完成、↷ 略過（附原因）、⟲ 使用快取（費用為 0）、✘ 失敗（已改用規則後備）。
- 每完成一項就更新實際 Token 與費用；服務商沒有回報用量時標示「未回報，按預估計」。

- 完成後顯示「實際與預估對照」，並寫入 `ai_tasks` 資料表，供用量儀表板與校準使用。
- 技術上沿用現有的 `jobs.py` 輪詢（每秒一次），新增 `job["ai_tasks"]` 陣列即可，不必改用 WebSocket。

## 9. 其他建議

1. **先讓 AI 說真話（P0）：** 立即修正 `ai_plan` 的預覽文字與實際行為不符的問題，並移除從未執行的「投行對照」步驟，或把它真正接上。這是信任問題，應比新功能優先。
2. **金融業改用正確方法：** 在完成 DDM／RI 之前，通用規格遇到銀行、保險應拒絕估值並說明原因（與現時拒絕虧損公司的做法一致），不要輸出看似精確但方法錯誤的數字。
3. **追蹤 AI 預測準確度：** 每次新財報公布時，把上一次 T3 的首年預測與實際值比較，記錄 AI 與規則後備各自的誤差，並在「紀錄」分頁顯示。這是判斷 AI 是否物有所值的唯一客觀方法，也能據此調整任務設計。
4. **本機服務加固：** 加入 `TrustedHostMiddleware`（只接受 `127.0.0.1`／`localhost`），變更設定的端點要求每次啟動時產生的工作階段令牌，防止 DNS rebinding 改寫 API 位址並竊取金鑰。
5. **分開測試基準與執行輸出：** 把 `out/`、`cases/` 中的基準檔移到 `tests/fixtures/`，讓真實估值不再令測試失敗；再加上 GitHub Actions 持續整合（Windows、macOS、Linux 各跑一次 pytest）。
6. **命令列日期：** 把 `--date` 預設改為澳門時間的今天（須同時更新鎖定它的測試）。
7. **觀察名單與提醒：** 對已估值的股票每日只更新市價（零 AI 費用），市價跌破悲觀價或升穿樂觀價、或有新財報時提醒；本機可用作業系統通知，或沿用現有的電郵設定。
8. **資料來源備援：** `yfinance` 屬非官方介面，隨時可能失效。美股以 SEC XBRL 為主、Yahoo 為輔；為每個資料源加健康檢查，失敗時明確標示資料缺口。
9. **合規標示：** 所有 AI 產生的文字加上「AI 產生」標記與模型名稱；免責聲明延續現有寫法。

## 12. 風險與緩解

| 風險 | 影響 | 緩解 |
| --- | --- | --- |
| AI 編造數字或來源 | 錯誤估值 | 引用驗證、數值護欄、人工採用、反方審查 |
| 公告或新聞內含提示注入 | AI 被操控 | 資料與指令分區、Schema 白名單、不可信文字不進系統指令 |
| 價格表過時 | 費用預估失準 | 查價日期、超過 90 天提示、以服務商回報用量計算實際費用 |
| 資料源失效（yfinance） | 無法估值 | 多來源、健康檢查、明確資料缺口 |
| 介面大改令現有用戶不習慣 | 使用率下降 | 保留 Excel 檢視、提供設定切回舊版一個版本週期 |
| 多方法令結果看似更確定 | 過度自信 | 足球場圖顯示範圍、信心等級、方法分歧大時警示 |
